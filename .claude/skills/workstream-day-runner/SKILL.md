# workstream-day-runner

팀장(이 스킬을 실행하는 당신)이 **"N일차 진행"** 한 마디로 한 회차 분량의 작업을
산정해 **사람이 읽는 회차 브리핑으로 먼저 알려주고**, 병렬 서브에이전트로 굴린 뒤
교차검증·문서갱신·워크로그·git 커밋까지 끝내는 절차다.

이 프로젝트의 계획 문서에는 "일차(Day)" 개념이 없다 — 스케줄 단위는 주차이고,
`docs/SCHEDULE/SCHEDULE.md`는 실작업 **1~28주차에 버퍼 5주**를 얹어 총 33주로 잡아 뒀다. 그래서
**"일차 = 진행 회차"** 로 다룬다 — 주차와 무관하게, 선행조건이 충족된 다음 Task 배치를
회차마다 하나씩 진행한다. `N`은 몇 번째 회차인지를 가리키는 카운터일 뿐이다.

**주차 표기는 회차 모드에서 "순서"로만 읽는다.** SCHEDULE과 work 문서의 주차·날짜는 캘린더 일정을
전제로 산정한 값이고, 회차 운영은 그 숫자를 다시 계산하지 않는다. "3주차 Task가 3회차에 열린다"는 뜻이
아니라 **주차가 이른 Task가 먼저 열린다**는 순서 정보로 쓴다. 배치 판정의 실제 기준은 언제나
`의존:`·`선행 대기:` 두 필드다.

**배정 단위는 사람이 아니라 업무 영역(워크스트림)이다.** `schedule-planner`가 산출한
`docs/ROADMAP/work/NN.<영역>.md`가 "누가 무엇을 하는가"의 단일 소스이고, 서브에이전트는
**한 워크스트림을 맡는 실행 주체**다. 인물 이름·프로필·팀 편성은 이 절차 어디에도 없다.

## 0. 역할과 불변 원칙

- **팀장만** "N일차 진행" 지시를 처리한다. 실제 구현은 워크스트림 서브에이전트가 하고, 팀장은
  계획·소환·검증·문서화·커밋을 맡는다. 팀장이 직접 코드를 쓰지 않는다.
- **워크스트림 수 = `docs/ROADMAP/work/` 하위 파일 수.** 파일명이 곧 워크스트림이다
  (`01.<영역>.md` 형식). 개수를 코드에 박지 말고 실행 때마다 `docs/ROADMAP/work/`를 나열해
  정한다(파일이 늘면 워크스트림도 는다). **`상태: 비활성`인 문서는 배정 대상에서 뺀다.**
- **워크스트림 소환은 `Agent(subagent_type: "general-purpose", model: "sonnet")` 로 한다.**
  타입과 모델을 바꾸지 않는다(근거는 2절·0-2절).
- **각 에이전트의 읽기 범위는 자기 워크스트림 문서를 축으로 한다.** `docs/ROADMAP/work/NN.<영역>.md`가
  기준이고, **다른 워크스트림의 work 문서는 읽지 않는다.** 아래 넷은 **상시 허용**이며, 소환 프롬프트에
  적혀 있지 않아도 에이전트가 스스로 판단해 읽는다:
  - **담당 Task의 `docs/ROADMAP.md` `### Task NNN` 블록은 반드시 읽는다.** 「생성/수정 파일」·
    「구현 규칙」·「완료 조건 (DoD)」이 거기에만 있다. work 문서에는 제목·공수·기간·의존만 적혀 있어서,
    이 블록을 안 읽으면 무엇을 만들지도 무엇으로 완료를 판정하는지도 모르는 채 착수하게 된다.
    **읽기만 하고 편집은 금지다** — 완료 체크와 진행률 갱신은 팀장 전용이다(4단계 2항).
  - **work 문서 각 Task의 `참조:` 줄에 적힌 문서는 종류를 불문하고 항상 읽는다**
    (`docs/PRD.md`·`docs/kiwi-verification.md`·`docs/screens/*` 등). 그 줄이 곧 그 Task의 필수 입력이다.
  - **`docs/CONVENTIONS.md`는 모든 에이전트가 항상 읽는다.** 디렉터리·명명·식별자·서버 전용 코드·
    응답 형식·화면 규약의 단일 소스이고, 여러 워크스트림이 같은 코드베이스에 쓰기 때문에 판단이 갈리면 안 된다.
  - 작업 종류에 따라 **0-2절이 허용하는 참조 문서**(`docs/screens/`, Next.js 구조 지침)도 읽는다.
  (프로젝트 공통 지시인 `CLAUDE.md`/`AGENTS.md`는 모든 에이전트에 항상 적용된다 — Next.js 코드를 쓰기 전에
  `node_modules/next/dist/docs/`의 설치본 문서를 먼저 읽는다.)
  허용은 거기까지다 — 다른 워크스트림의 work 문서를 여는 근거가 되지 않는다.
- 문서 SSOT를 지킨다: 영역 정의·Task·공수·주차·의존=`docs/ROADMAP/work/`,
  전체일정=`docs/SCHEDULE/SCHEDULE.md`. 데이터를 복제하지 말고 각 소스를 참조/갱신한다.
- **`docs/team/`은 없다.** 인물 프로필을 찾지 말고 만들지도 않는다. 옛 회차 문서에
  `docs/team/`·`docs/ROADMAP/team/` 경로가 남아 있으면 각각 폐지·`docs/ROADMAP/work/`로 읽는다.

아래 1→1-1→2→3→4 순서대로 진행한다. **1-1(회차 브리핑)을 건너뛰고 spawn하지 않는다.**
**4단계(완료 처리)는 3단계에서 이슈가 완전히 0이 된 뒤에만** 한다.

## 0-1. 공유 문서(`docs/ISSUES.md`·`docs/DECISIONS.md`) 동시편집·번호 부여 규칙

**이 규칙이 막는 실패**: 여러 워크스트림이 같은 회차에 `docs/ISSUES.md`(이슈 번호 `I-NNN`)·
`docs/DECISIONS.md`(결정 번호 `D-NNN`) 본문 끝에 동시에 append하면 번호가 충돌한다.
"다음 번호"를 grep으로 확인해도 소용없다 — 확인과 쓰기 사이의 간격에서 다른 워크스트림이 같은 번호를
먼저 써 버리고, 서브에이전트들은 서로의 진행을 볼 수 없어 그 간격을 스스로 좁힐 방법이 없다.
번호가 겹치면 되돌리는 비용이 크다: 이미 다른 문서·커밋 메시지·draft가 그 번호를 인용하기 시작하므로
정정이 한 파일에서 끝나지 않는다.

- **워크스트림이 직접 해도 되는 것과 안 되는 것을 가르는 기준은 "새 번호가 생기는가"다.**
  금지되는 것은 **`### I-NNN` / `### D-NNN` 새 헤딩을 워크스트림이 직접 붙이는 것**뿐이다 — 이게
  번호 충돌의 유일한 발생 지점이기 때문이다. **이미 번호가 있는 기존 블록 안의 내용은**
  `상태` 필드 갱신(열림→해결됨 등)이든, 진행 상황 메모·교차 참조를 한 줄 추가하는 것이든
  **새 번호를 만들지 않는 한 직접 고쳐도 된다** — 헤딩 하나 안에서 끝나는 블록 내 수정이라
  충돌 지점이 아니다.
- 새 이슈·결정은 각자 `docs/ISSUES.draft.<AREA>.md` / `docs/DECISIONS.draft.<AREA>.md`에
  **번호 없이** 제목·근거·본문만 쓴다.
- **번호 부여(`I-NNN`/`D-NNN`)와 두 파일 본문으로의 병합은 회차 마감(아래 4단계 "완료
  처리")에 팀장 한 명만 한다.** 병합 후 draft 파일은 삭제한다.
- 병합 시 문서 간 또는 문서-실물 사이에 값이 어긋나면 **`data/` 하위의 실제 파일과 커밋된 코드 쪽을
  진실로 삼는다** — 문서는 한 줄 고치면 되지만 이미 저장된 데이터와 동작하는 코드는 되돌리는 비용이 더 크다.
- **기각된 대안**: 회차 시작에 팀장이 번호 자리를 미리 예약(`### D-NNN · (예약: AREA, 미작성)`)해 두는
  방식 — 회차 중 배정이 바뀌면(어느 워크스트림이 유휴로 빠지거나 draft를 결국 안 쓰는 등) 빈 예약 번호가
  남고, 그 자리를 누가 쓰는지가 다시 조정 대상이 되어 예약 자체가 새 충돌원이 된다.

이 절은 3단계(교차검증 루프)에서 이슈를 발견해 등재할 때와 4단계(완료 처리)에서 문서를
갱신할 때 모두 적용된다. **`docs/CONVENTIONS.md`는 코드 디렉터리·명명 규약의 단일 소스이고
이 규칙은 회차 운영 절차이므로 여기(SKILL.md)에 둔다** — 두 곳에 중복 등재하지 않는다
(`docs/CONVENTIONS.md`에는 이 절을 가리키는 참조 한 줄만 남겼다).

## 0-2. 작업 종류별 참조 문서 (화면 UI · Next.js)

0절의 읽기 범위 제한에 대한 **명시적 예외**다. 아래 두 종류의 작업에서는 워크스트림 문서 외에
지정된 참조 문서를 반드시 함께 읽는다.

**이 예외는 상시 권한이다 — 팀장이 열어 줘야 읽을 수 있는 게 아니다.** 담당 Task가 아래 종류에
해당하면 소환 프롬프트에 참조 블록이 붙어 있지 않아도 워크스트림 에이전트가 **스스로 판단해
읽는다.** 소환 프롬프트의 참조 블록(2단계)은 **팀장이 경로를 미리 찾아 주는 편의 장치**일 뿐,
읽기 권한의 관문이 아니다 — 팀장이 붙이는 걸 잊어도 참조가 누락되지 않게 하려는 이중 안전장치다.
리뷰 상대는 **참조 문서와의 일치 여부를 교차검증한다**(3단계) — 이게 세 번째 안전망이다.

### 화면(UI) 작업 → `docs/screens/`

**대상**: 페이지·레이아웃·컴포넌트의 마크업과 스타일을 만들거나 고치는 모든 Task.

- **진입점은 `docs/screens/README.md`다.** 여기 있는 **라우트 ↔ 파일 ↔ 화면 문서 매핑표**와
  **화면별 필요 shadcn 컴포넌트 목록**을 먼저 읽고, 자기 Task가 건드리는 화면의 문서만 골라 읽는다.
  매핑표를 이 SKILL.md에 복사하지 않는다 — README가 단일 소스이고, 화면이 늘면 거기서만 는다.
- **`00-app-shell.md`(공통 앱 셸)은 화면 Task라면 항상 함께 읽는다.** 헤더·내비게이션·컨테이너·
  토스트가 모든 페이지 공유분이라, 개별 화면만 보고 만들면 셸과 어긋난다.
- **화면 설계서가 정적 마크업·레이아웃의 단일 소스다.** 문서에 있는 요소·상태·라벨을 빠뜨리지 말고,
  **문서에 없는 UI를 임의로 지어내지 않는다.** 설계서가 실제 요구와 어긋나 보이면 혼자 판단해서
  바꾸지 말고 `docs/ISSUES.draft.<AREA>.md`에 올린다(0-1절).
- **화면 설계서는 로직·상태 관리·데이터 페칭을 다루지 않는다**(README 명시). 그 부분은 `docs/ROADMAP.md`
  해당 Task 블록의 「구현 규칙」과 `docs/CONVENTIONS.md`를 따른다. 설계서에 없다고 해서 로직을
  생략해도 된다는 뜻이 아니다.
- 새 shadcn 컴포넌트 설치가 필요하면 **직접 설치하지 말고 팀장에게 보고한다** — 설치는 회차 단위로
  팀장이 한 번에 처리해야 `package.json` 동시 편집 충돌이 안 난다.
- 화면 Task가 아닌 워크스트림(저장소·파이프라인 등)은 `docs/screens/`를 읽지 않는다. 다만 **자기가 만든
  API의 응답 형태가 어느 화면에 쓰이는지 확인할 때는 해당 화면 문서 한 건까지** 열어봐도 된다.

### Next.js 개발 → `.claude/agents/dev/nextjs-app-developer.md`

**대상**: App Router 구조에 손대는 작업 — 라우트·폴더 구성, `layout.tsx`·`page.tsx`·`loading.tsx`·
`error.tsx`·`not-found.tsx`·`route.ts` 같은 파일 컨벤션, 서버/클라이언트 컴포넌트 경계, 메타데이터,
라우트 그룹·병렬·인터셉트 라우트, 스트리밍/Suspense 구성.

- 이 파일을 **App Router 구조 설계 지침서로 읽는다.** 파일 컨벤션과 구조 패턴, 서버/클라 경계 판단
  기준을 여기서 가져온다. 문서 앞부분의 **「⚠️ Next.js 16 기준 — 15에서 달라진 것」 표를 먼저 본다** —
  훈련 데이터에 남은 15 시절 패턴(`middleware.ts`, 병렬 라우트 `default.tsx` 누락, 1인자
  `revalidateTag` 등)을 그대로 쓰면 빌드가 깨진다.
- **버전 우선순위는 그대로 유효하다.** 지침서는 **Next.js 16 기준으로 갱신**되어 있지만, 그래도
  API 시그니처·기본값·동작이 어긋나면 **`node_modules/next/dist/docs/`의 설치본 문서가 이긴다**
  (`AGENTS.md`의 최우선 지시). 지침서가 낡을 수 있고 설치본은 낡을 수 없기 때문이다.
  둘이 다르면 지침서를 따라 코드를 쓰지 말고, 어긋난 지점을 draft 이슈로 남긴다.
- **설치 버전을 실행 시점에 확인한다**: `node -p "require('./node_modules/next/package.json').version"`.
  지침서의 기준선(16)과 메이저가 다르면 그 사실을 팀장에게 보고한다 — 지침서 갱신이 필요하다는 신호다.
- **서브에이전트 타입을 `nextjs-app-developer`로 바꾸지 않는다.** 워크스트림 에이전트는 영역 경계·
  리뷰 상대·draft 이슈 규칙까지 함께 지고 있어야 하므로, 소환은 **`Agent(subagent_type: "general-purpose",
  model: "sonnet")` 그대로 두고** 이 파일을 **읽기 자료로** 준다(2절). 전문 에이전트로 갈아끼우면
  그 규칙들이 통째로 빠진다.

## 1. 착수 — 회차 판정과 shrimp 계획 수립

1. **N 확정.** 사용자 지시에서 회차 번호를 읽는다("3일차 진행" → N=3).
2. **완료 집합 파악.** `docs/dailyWorkLog/`의 기존 `*_Day.md`를 훑어 지금까지 완료된 Task 번호를
   모은다(디렉터리가 없으면 공집합 = 아직 아무 회차도 안 함). `N-1_Day.md`가 없는데 N≥2이면
   회차를 건너뛴 것이므로 사용자에게 알리고 계속할지 확인한다.
3. **이번 회차 대상 배치 산정.** `docs/ROADMAP/work/*.md`의 각 Task에서 `의존:`·`선행 대기:`
   필드만 읽어(문서 본문은 최소한으로) 아래를 만족하는 **미완료 Task**를 고른다:
   - `의존:`의 모든 Task가 완료 집합에 있음, **그리고**
   - `선행 대기:`의 모든 타 영역 Task가 완료 집합에 있음.
     이 조건을 만족하는 Task 묶음이 이번 회차 배치이고, 그 Task를 담당하는 워크스트림이
     **이번 회차 활성 워크스트림**이다.
     (`선행 대기: 없음`·`의존: 없음`인 Task는 항상 착수 가능 → 보통 1일차의 시작점.)

   **조각 번호 정규화 — 반드시 먼저 적용한다.** 10인일을 넘는 Task는 `008A`·`008B`처럼 조각으로
   쪼개져 있고 완료·배정 단위도 조각이다. 그래서 의존 표기에 원 Task 번호(`008`)와 조각 ID(`008A`)가
   섞여 나올 수 있다. 대조 전에 아래로 통일한다:
   - **원 Task 번호로 적힌 의존은 그 번호의 모든 조각이 완료 집합에 있을 때만 충족된 것으로 본다.**
     `의존: Task 008`은 `008A`와 `008B`가 둘 다 끝나야 풀린다. 한쪽만 끝난 상태로 통과시키면
     아직 없는 산출물을 전제한 Task가 열린다.
   - 조각 ID로 적힌 의존은 그 조각만 대조한다(`의존: Task 008A` → `008A`만 보면 된다).
   - 완료 집합에도 같은 규칙을 쓴다 — 워크로그에 `008A`만 적혀 있으면 `008`은 미완료다.
   - 표기가 어느 쪽인지 판단이 안 서는 Task가 있으면 넘겨짚지 말고 브리핑에 적어 사용자에게 확인받는다.
4. **유휴 워크스트림 처리.** 위 배치에 열린 Task가 하나도 없는 워크스트림에는 그 영역 문서
   §「유휴 주에 맡길 것」 표의 **「맡길 것」 항목을 이번 회차 작업으로 배정한다.** 여기에는 다른 Task의
   DoD가 요구하는 준비물이 들어 있어서(예: 013B의 실언론사 3곳 피드 조사, 010A의 인코딩 확인 자산),
   수행 주체를 정하지 않으면 그 Task가 열리는 회차에 검증을 못 해 완료 판정이 막힌다.
   **배정할 「맡길 것」이 없으면 그 워크스트림은 이번 회차에 소환하지 않는다.** 유휴 배정으로 소환한
   워크스트림도 활성으로 취급해 3단계 교차검증과 워크로그 기록에 포함한다.
5. **shrimp-task-manager로 계획 수립.** 배치가 정해지면 곧바로:
   - `mcp__shrimp-task-manager__plan_task` 로 이번 회차 목표를 기술하고,
   - `mcp__shrimp-task-manager__split_tasks` 로 **워크스트림별 하위 태스크**로 쪼개 등록한다
     (태스크 이름에 담당 영역명과 원 Task 번호를 넣어 추적 가능하게).
   - 진행 중 상태 갱신은 `update_task`, 목록 확인은 `list_tasks`, 완료 판정은 `verify_task`.

   **shrimp 등록은 브리핑(1-1절) 뒤에 한다.** 사용자가 브리핑을 보고 회차를 중단시킬 수 있으므로,
   먼저 브리핑을 내고 계속 진행이 확정된 뒤에 등록한다.

산정이 끝나면 **1-1절 회차 브리핑**을 낸 뒤 2단계로 넘어간다.

## 1-1. 회차 브리핑 — "이번 회차에 뭘 하는지" 사람이 읽는 요약

배치를 산정한 직후, **서브에이전트를 하나도 띄우기 전에** 이번 회차에 무슨 일을 하는지
사용자에게 요약해 보여준다. 이걸 건너뛰고 곧장 spawn하지 않는다.

**목적**: 팀장이 뭘 굴리려는지 사용자가 3초 만에 파악하고, 잘못 잡혔으면 시작 전에 잡는다.

### 서식

Task 하나당 **제목 한 줄 + 설명 한두 문장 + 산출물 한 줄**이다. 표를 쓰지 않는다.

```markdown
## N일차에 할 일

<이번 회차가 무슨 회차인지 한 문장. 지난 회차에 무엇이 끝나서 이 일들이 열렸는지 함께.>

**<영역명>** — <Task 제목을 쉬운 말로> (Task NNN · 약 N.N인일)
<이 일이 무엇이고 왜 지금 필요한지 한두 문장. 문서 문장을 복붙하지 말고 다시 쓴다.>
→ <만들 파일·산출물 경로>

(활성 워크스트림 수만큼 반복)

**진행 순서**: <동시에 시작하는 영역 / 무엇이 끝나야 무엇이 붙는지 한 줄. 릴레이가 없으면 "세 갈래 모두 동시 시작".>
**이번엔 안 하는 것**: <가까운데 아직 안 열린 Task 한두 개와 그 이유. 없으면 이 줄을 뺀다.>
```

### 문체 규칙 — 사람이 알아볼 수 있게

- **문서 필드를 그대로 덤프하지 않는다.** `의존: Task 004 / 선행 대기: 없음 / 공수: 9.9인일 (L)`처럼
  나열하는 건 금지다. 필요한 사실은 문장 안에 녹인다("004가 끝나서 이제 열렸다").
- **Task 제목을 그대로 쓰지 말고 한 번 풀어 쓴다.** "파일 저장소 공통 기반 (경로 · 원자적 쓰기 · 시드)"
  → "파일을 안전하게 읽고 쓰는 바닥을 깐다 — 크롤이 쓰는 중에 화면이 읽어도 깨지지 않게."
- **약어·내부 기호는 처음 나올 때 풀어 준다.** 기능 ID(`F001`~`F008`)나 이슈·결정 번호(`I-NNN`·`D-NNN`)를
  근거로 들 때는 "…기능(F00N)", "…결정(D-00N)"처럼 무엇인지 한 마디로 붙인다. 번호만 던지지 않는다.
- **보고서 투를 쓰지 않는다.** "본 회차에서는 ~을 수행합니다", "~하도록 하겠습니다", "총 N개의 태스크를
  처리 예정입니다" 금지. 프로젝트 문서와 같은 **단정적 평서체**로 쓴다.
- **숫자는 있는 것만.** 공수(인일)와 Task 번호는 적고, 진행률·백분율·예상 소요 시간은 지어내지 않는다.
- **이모지·구분선·굵게를 남발하지 않는다.** 굵게는 영역명과 라벨에만 쓴다.
- **길이 상한**: 활성 워크스트림 3개 기준 **15줄 이내**. 자세한 건 워크스트림 문서에 이미 있다.
- **인물 이름을 쓰지 않는다.** 주체는 업무 영역이다(0절 원칙).

### 브리핑 뒤 처리

- 기본은 **승인을 기다리지 않고** 그대로 2단계(spawn)로 넘어간다. "N일차 진행"은 이미 실행 지시다.
- 다만 아래 경우엔 브리핑을 낸 자리에서 **멈추고 사용자 답을 기다린다**:
  - 사용자가 계획만 물어본 경우("3일차 뭐 해?", "계획만 보여줘") — 브리핑이 최종 산출물이다.
  - 1절 2번의 **회차 건너뜀 경고**가 걸린 경우.
  - 배치가 비었거나(열린 Task 0건), 활성 워크스트림이 하나도 없는 경우 — 왜 비었는지(무엇이 선행으로
    막고 있는지)를 브리핑 자리에 대신 적고 멈춘다.

### 예시

```markdown
## 3일차에 할 일

2일차에 도메인 타입과 zod 스키마(Task 004)가 끝나면서, 그 위에 얹히는 저장 계층 작업 두 갈래가 열렸다.

**저장소 계층** — 파일을 안전하게 읽고 쓰는 바닥 깔기 (Task 005 · 약 8.6인일)
크롤이 파일을 쓰는 도중에 화면이 그 파일을 읽어도 깨지지 않도록 원자적 쓰기와 경로 규칙, 초기 시드를 잡는다.
앞으로 모든 레포지토리가 이 위에 올라간다.
→ `lib/storage/` 하위 공통 모듈

**크롤 파이프라인** — 수집 결과를 담을 저장소 (Task 007 · 약 7.2인일)
실행 기록·기사·키워드를 파일로 남기는 레포지토리다. 크롤러가 직접 쓰는 쪽이라 저장소 계층과 나눠 맡는다.
→ `lib/repositories/` 실행·기사·키워드 3종

**진행 순서**: 두 갈래 동시 시작. 다만 크롤 파이프라인은 저장소 계층의 공통 기반이 나온 뒤 그 위에 붙인다.
**이번엔 안 하는 것**: 언론사 CRUD API(Task 008)는 레포지토리(006)가 끝나야 열린다.
```

## 2. 의존성 순서 spawn (릴레이)

이번 회차 배치 **안에서도** 워크스트림 간 선후가 있을 수 있다(A의 산출을 B가 받아 씀). 그래서
무조건 동시에 띄우지 않고 위상 정렬해서 소환한다.

- **소환 형태는 `Agent(subagent_type: "general-purpose", model: "sonnet")` 로 고정한다.**
  워크스트림 에이전트는 영역 경계·리뷰 상대·draft 이슈 규칙까지 함께 지고 있어야 하므로 범용 타입을 쓰고,
  필요한 지침서는 프롬프트에 **읽기 자료로** 준다(0-2절). 전문 에이전트 타입으로 갈아끼우지 않는다 —
  그 규칙들이 통째로 빠진다.
- **선행이 없는 활성 워크스트림**은 한 메시지에 여러 `Agent` 호출로 **동시에** 소환한다.
- **선행이 있는 워크스트림**은 그 선행 워크스트림의 작업이 **끝난 뒤에** 소환한다
  (사용자 요구: "선행작업 완료 후 spawn"). 선행 완료 통지를 받고 나서 다음을 띄운다.
- 각 소환 프롬프트는 `references/workstream-spawn-prompt.md` 템플릿을 채워 쓴다. 반드시 포함:
  읽기 범위(자기 워크스트림 문서 + 0절 상시 허용 4종), 이번 회차 담당 Task 번호와 요약,
  산출물 경로/형식, `docs/CONVENTIONS.md` 준수, DoD 자기 점검 결과 보고.
- **0-2절 참조 블록을 팀장이 판단해 붙인다.** 담당 Task가 화면(UI) 작업이면 템플릿의
  `[화면(UI) 작업 — 참조 문서]` 블록을, App Router 구조에 손대는 작업이면
  `[Next.js 구조 작업 — 참조 문서]` 블록을 채워 넣는다(둘 다 해당하면 둘 다). 해당 없으면 뺀다.
  블록에 화면 문서 경로까지 찾아서 적어 주면 에이전트가 문서를 뒤지는 시간을 아낀다.
  **다만 이건 편의 장치이고 관문이 아니다** — 0-2절이 상시 권한이므로, 팀장이 블록을 빠뜨려도
  에이전트는 자기 Task 성격을 보고 참조 문서를 읽는다. 붙였는지 여부로 참조 성패가 갈리지 않는다.
- **소환한 에이전트의 agentId를 보관한다.** 이후 수정·재검증·종료에서 같은 에이전트를 이어 써야
  컨텍스트가 유지된다. 수정 지시는 새로 spawn하지 말고 `SendMessage`로 기존 에이전트에 보낸다.

모든 활성 워크스트림이 1차 산출을 끝내면 3단계로 간다.

## 3. 교차검증 루프 (이슈가 0이 될 때까지 반복)

활성 워크스트림끼리 작업 내용을 **상호 공유**하고 **교차 점검**한다. 누가 누구를 검증하는지는
각 워크스트림 문서(`docs/ROADMAP/work/NN.*.md`) 「영역 정의」 표의 **`리뷰 상대`** 행을 그대로
쓴다 — `schedule-planner` 규칙 7이 이미 담당 ≠ 리뷰가 되도록 순환시켜 놓았다. 리뷰 상대가
이번 회차에 활성이 아니면 활성 워크스트림 중 담당과 다른 영역에 검증을 맡긴다.

검증 항목에는 산출물 정확성뿐 아니라 **프로젝트 규약 위반**도 포함한다(체크리스트):

- **담당 Task의 `docs/ROADMAP.md` 「완료 조건 (DoD)」 체크박스를 하나씩 대조한다.** 통과하지 못한 항목이
  하나라도 있으면 **그 Task는 완료가 아니다.** "대체로 됐다"로 넘기지 않고 항목별 pass/fail을 남긴다 —
  이 결과가 워크로그 「DoD 충족 현황」에 그대로 들어간다.
- **「구현 규칙」의 각 불릿을 준수했는지 대조한다.** 특히 **⚠️ 표시가 붙은 함정 항목**은 지키지 않아도
  빌드·타입체크가 통과하고 화면도 멀쩡해 보이므로, 여기서 잡지 못하면 아무도 못 잡는다.
- **`docs/CONVENTIONS.md` 준수 여부.** 식별자 형식, `import 'server-only'`, `globalThis` 싱글턴,
  `runtime` export 금지, 응답 봉투(`ok`/`fail`)와 상태 코드, 디자인 토큰·lucide 신 별칭·`next/link`까지
  해당 항목만 골라 대조한다.
- **화면(UI) 작업이면 `docs/screens/`의 해당 문서와 대조한다**(0-2절): 설계서에 있는 요소·상태·라벨이
  빠지지 않았는가, **설계서에 없는 UI를 지어내지 않았는가**, 라우트와 파일 경로가 `README.md`
  매핑표와 같은가, 공통 앱 셸(`00-app-shell.md`)과 어긋나지 않는가.
- **App Router 구조에 손댔으면 `.claude/agents/dev/nextjs-app-developer.md`의
  「🚨 Next.js 16 필수 확인」 체크리스트로 대조한다**(0-2절). 특히 빌드를 깨는 것들:
  병렬 라우트 슬롯마다 `default.tsx`가 있는가, 요청 가로채기가 `middleware.ts`가 아니라
  **`proxy.ts`**인가, `params`·`searchParams`·`cookies()`·`headers()`를 전부 `await` 하는가,
  `revalidateTag`에 두 번째 인자를 넘겼는가. 서버/클라 경계(`error.tsx`는 클라이언트 컴포넌트)도 본다.
  **판정 근거가 갈리면 설치본 `node_modules/next/dist/docs/`가 최종 판정 기준이다** — 지침서를
  근거로 설치본과 맞는 코드를 틀렸다고 하지 않는다.

**화면·API Task는 Playwright MCP 동선을 실제로 태운 뒤에만 완료로 본다.** `docs/ROADMAP.md`의
「🧭 작업 진행 규칙」 3번이 이를 완료 판정으로 걸어 두었고, 이 프로젝트는 `@playwright/test` E2E 스위트를
도입하지 않기로 했으므로(`docs/CONVENTIONS.md` §9) **이것이 유일한 기능 검증 수단이다.** lint·typecheck·
build는 응답 형태가 틀려도, 설계서의 화면 상태 일부를 빠뜨려도 전부 통과한다. 그러니 해당 Task의 DoD에
적힌 동선을 브라우저에서 그대로 태우고, 무엇을 눌러 무엇을 확인했는지 한 줄로 기록한다. 동선을 태우지
못했으면 그 Task는 미완료이며, 태울 수 없는 이유(선행 API 부재 등)를 이슈로 남긴다.

**이슈가 발견되면 이슈가 사라질 때까지** 다음 6단계를 반복한다:

1. 이슈 내용을 **해당 워크스트림에 전달**한다(`SendMessage`로 그 에이전트에).
2. 그 워크스트림이 **수정 작업**을 한다.
3. 수정 완료 후 **리뷰 상대 워크스트림이 교차 재검증**한다.
4. 이슈가 해결되면 **팀장에게 보고**한다.
5. 팀장이 **전체 테스트**를 이 순서로 돌린다:
   `npm run lint` → `npm run typecheck` → `npm run test` → `npm run build`.
   회차 내용과 무관하게 **네 명령을 항상 실행**하고 각 결과를 기록한다(문서만 바뀐 회차라도 실행해
   기존 코드가 깨지지 않았음을 보장한다). 실행 자체가 불가능한 상황(예: 의존성 미설치)이면 그 원인을
   먼저 해소한 뒤 실행한다. 싼 검사부터 돌려야 실패를 빨리 만난다 — build가 가장 오래 걸린다.
   `npm run test`는 vitest로 `lib/**/*.test.ts`만 돌린다(`docs/CONVENTIONS.md` §9). `vitest.config.mts`에
   `passWithNoTests: true`가 걸려 있어 대상 파일이 아직 없으면 통과로 끝나므로, 그 경우엔 "테스트 파일
   없음"이라고 그대로 기록한다.
   **`npx tsc --noEmit`을 직접 부르지 않는다.** `npm run typecheck`는 `next typegen && tsc --noEmit`이고,
   `next typegen`이 만드는 `PageProps`·`LayoutProps`·`RouteContext` 전역 타입이 있어야 App Router
   코드의 타입 검사가 성립한다. `tsc` 단독 실행은 그 타입들을 못 찾아 엉뚱한 오류를 내거나,
   생성 타입을 안 쓰는 코드에서는 검사가 헐거워진다.
   (`npm run lint`는 ESLint를 직접 부른다 — Next.js 16에서 `next lint`는 제거됐고 `next build`도
   더는 린트를 돌리지 않으므로, 이 명령을 빼면 린트가 아예 실행되지 않는다.)
6. 테스트에서 이슈가 나오면 1번으로 회귀, 없으면 검증 종료.

이슈가 0이고 전체 테스트가 통과해야 4단계로 넘어간다.

## 4. 완료 처리 (이슈 0 · 테스트 통과 시에만)

순서대로 수행한다.

1. **스케줄 문서 갱신.** 이번 회차에 완료한 각 Task에 대해 `docs/ROADMAP/work/NN.*.md`의
   해당 Task 불릿에 상태 마커를 추가/갱신한다:
   `- 상태: 완료 (N일차, YYYY-MM-DD)`
   (Task 상태의 SSOT는 이 문서다. 날짜는 시스템 오늘 날짜.)
2. **전체 로드맵(`docs/ROADMAP.md`) 완료 반영.** **회차가 끝날 때마다 반드시 한다.**
   Task 상태의 SSOT는 `docs/ROADMAP/work/`지만 `docs/ROADMAP.md`는 사람이 보는 전체 진행 현황판이므로,
   회차마다 같은 사실을 여기에도 반영해 두 문서가 어긋나지 않게 한다.
   **이 파일은 팀장만 고친다** — 워크스트림 에이전트가 직접 편집하면 `ISSUES.md`와 같은 동시편집 충돌이
   나므로(0-1절), 소환 프롬프트에도 "ROADMAP.md는 건드리지 않는다"를 넣는다.
   ROADMAP.md 「🧭 작업 진행 규칙」 4번이 요구하는 갱신을 그대로 수행한다:
   - **Task 상태 줄** — 해당 `### Task NNN` 블록 첫 줄의 `- [ ] 대기`를
     `- [x] 완료 (N일차, YYYY-MM-DD)`로 바꾼다. 같은 줄의 `기능 ID:`·`선행:` 필드는 그대로 둔다.
   - **결과물 줄** — 실제로 만든/고친 파일이 계획과 다르면 `- **결과물**:` 줄을 실물 기준으로 정정한다.
     계획과 달라진 판단이나 남은 제약이 있으면 `- **남긴 한계**:` 한 줄을 덧붙인다.
   - **「🗺️ 전체 진행률 요약」 표** — 해당 Phase 행의 `완료` 수와 `상태`(⬜ 대기 / 🟡 진행 중 / ✅ 완료)를
     갱신하고, **합계 행의 완료 수와 백분율(완료/전체, 정수 반올림)까지 다시 계산한다.**
   - **Phase 제목** — 그 Phase의 Task가 전부 완료되면 제목 끝에 `✅`를 붙인다.
   - **「📊 현재 상태 (as-is)」 표** — 해당 영역의 실체가 실제로 바뀐 경우에만 그 행을 고친다.
     기본은 건드리지 않는다.
   - **완료하지 못한 Task는 절대 체크하지 않는다.** 체크 근거는 3단계에서 이슈 0 + 전체 테스트 통과가
     확인된 Task뿐이다. 부분 진행은 체크 없이 `- **진행 메모**:` 한 줄로만 남긴다.
   - **조각(`NNNA`·`NNNB`)은 원 Task 블록 하나에 대응한다.** 회차 완료 단위는 조각이지만
     `docs/ROADMAP.md`에는 `### Task NNN` 블록이 하나뿐이므로, **원 Task의 모든 조각이 완료된
     회차에만 `- [x]`를 찍는다.** 일부 조각만 끝났으면 체크하지 않고
     `- **진행 메모**: NNNA 완료(N일차)` 한 줄만 남긴다. 조각 하나로 블록을 체크하면 아직 안 만든
     산출물까지 완료로 찍히고 진행률 표도 부풀려진다 — 바로 위 "완료하지 못한 Task는 절대 체크하지
     않는다"와 정면으로 어긋난다.
   - **진행률 표에는 체크된 블록만 센다.** 조각 단위 진행은 진행 메모로만 보이고 숫자에 들어가지 않는다.
3. **공유 이슈/결정 문서 병합.** **0-1절 규칙대로** 각 워크스트림의 `docs/ISSUES.draft.<AREA>.md`·
   `docs/DECISIONS.draft.<AREA>.md`를 팀장이 읽고, 이 시점에만 `I-NNN`/`D-NNN` 번호를 부여해
   `docs/ISSUES.md`·`docs/DECISIONS.md` 본문에 병합한다. 병합 후 draft 파일은 삭제한다.
4. **「영역 정의」 갱신은 필요할 때만.** `docs/ROADMAP/work/NN.*.md` 상단의 영역 정의 표는
   `상태` 행이 실제로 바뀔 때만 손댄다. 기본은 건드리지 않는다.
   **영역 범위·리뷰 상대가 바뀌어야 한다면 여기서 고치지 말고 `schedule-planner` 재산출로 넘긴다.**
5. **워크로그 작성.** `docs/dailyWorkLog/N_Day.md`를 `references/worklog-template.md` 서식으로 만든다
   (디렉터리가 없으면 생성). 회차 요약·워크스트림별 완료 Task·교차검증 결과·발견/해결 이슈·테스트 결과·
   다음 회차에 열리는 Task를 담는다. **이 파일이 다음 회차의 완료 집합 판정 근거**가 되므로
   완료 Task 번호를 빠짐없이 명시한다.
6. **문서 정합성 확인.** 이번 회차 완료 Task 번호 집합이 아래 세 곳에서 일치하는지 커밋 전에 대조한다:
   `docs/ROADMAP/work/NN.*.md`의 `상태: 완료` 마커, `docs/ROADMAP.md`의 `- [x] 완료` 체크,
   `docs/dailyWorkLog/N_Day.md`의 완료 Task 목록. 어긋나면 커밋하지 말고 먼저 맞춘다.
   **대조는 조각↔원 번호 매핑을 거쳐서 한다** — work 문서와 워크로그는 조각 ID(`008A`)로 적히고
   `docs/ROADMAP.md`는 원 번호(`008`)로 적힌다. 조각을 원 번호로 접은 뒤,
   **모든 조각이 완료된 원 번호만** `docs/ROADMAP.md`에 체크돼 있어야 한다. 일부만 끝난 원 번호는
   체크가 없고 `- **진행 메모**:` 줄이 있어야 정합이다. 번호가 그대로 다른 것만 보고 넘기지 않는다.
7. **에이전트 종료.** 보관해 둔 모든 활성 워크스트림 agentId에 `TaskStop`을 보낸다.
8. **git 커밋/푸시 (day-N 브랜치).**
   - 현재 브랜치에서 `git checkout -b day-N` (예: N=3 → `day-3`). main은 건드리지 않는다.
   - 변경을 스테이징하고 커밋한다. 커밋 메시지 말미에 **이번 실행 환경이 지정한 커밋 트레일러**
     (`Co-Authored-By:` · `Claude-Session:`) 두 줄을 그대로 붙인다.
     **모델명과 세션 URL을 이 문서에 박아 두지 않는다** — 값을 고정하면 다음 회차 커밋이
     지난 세션과 옛 모델을 가리키게 된다.
   - **push 전에 사용자 확인을 받는다.** 커밋까지 마친 뒤, 푸시할 브랜치(`day-N`)와 커밋 요약
     (변경 파일 수·완료 Task)을 사용자에게 보여주고 **"이 브랜치를 원격에 푸시할까요?"** 라고 명시적으로 묻는다.
     사용자가 승인하면 `git push -u origin day-N` 을 실행하고, 보류/거절하면 **커밋은 남겨 둔 채 푸시하지 않고**
     로컬 브랜치 상태만 보고한다.
   - 브랜치명 충돌 등으로 push가 막히면 사용자에게 상황을 보고하고 지시를 기다린다.

완료 후 사용자에게 **회차 요약**(활성 워크스트림, 완료 Task, 검증 결과, `docs/ROADMAP.md` 갱신 후 전체 진행률,
만든 워크로그 경로, 푸시한 브랜치)을 보고한다.
