# IT/AI 뉴스 핫 키워드 크롤러 MVP PRD

## 🎯 핵심 정보

**목적**: 체크박스로 고른 언론사에서 IT/AI 기사를 크롤링해 텍스트로 모으고, 형태소 분석으로 조사를 제거한 뒤 얼마나 자주 등장하는 단어인지 세어 핫 키워드를 뽑아내는 로컬 테스트 도구
**사용자**: IT/AI 뉴스에서 어떤 키워드가 많이 언급되는지 로컬 환경에서 빠르게 확인해보고 싶은 1인 개발자(운영자 본인)

## 🚶 사용자 여정

```
1. 크롤링 실행 페이지 (홈)
   ↓ 언론사 체크박스에서 대상 선택 (언론사 관리 페이지에 등록된 활성 언론사 목록 기준)
   ↓ [크롤링 시작] 버튼 클릭

2. 크롤링 진행 상태 확인 (크롤링 실행 페이지 내 실시간 표시)
   ↓ 크롤링 완료

3. 수집 결과 페이지
   ↓ 실행(run) 선택 → 저장된 기사 txt 목록/본문 확인
   ↓ [키워드 분석] 버튼 클릭

4. 핫 키워드 분석 페이지
   ↓ Kiwi 형태소 분석(조사·어미·접미사 제거) → 불용어 필터링 → 빈도 집계 → 랭킹 표시

   [분기 A] 랭킹에 "기자", "사진" 같은 상투어가 보임
     → 불용어 관리 페이지 이동 → 불용어 추가 → [재분석] → 4번으로 복귀(랭킹 갱신)

   [분기 B] 크롤링 대상 언론사를 늘리거나 줄이고 싶음
     → 언론사 관리 페이지 이동 → 언론사 추가/수정/삭제/활성 전환 → 1번으로 복귀(체크박스 목록에 즉시 반영)

5. 핫 키워드 랭킹 확인 후 종료, 또는 1번으로 돌아가 다른 언론사 조합으로 재크롤링
```

## ⚡ 기능 명세

### 1. MVP 핵심 기능

| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **F001** | 언론사 선택 크롤링 실행 | 체크박스로 선택된 언론사만 대상으로 크롤링. 언론사의 수집 방식(`sourceType`)에 따라 **RSS 피드 파싱** 또는 **목록 페이지 → 기사 링크 추출** 중 하나로 기사 URL을 얻고, 이어서 기사 본문을 수집 | 언론사를 직접 골라 대상을 통제하는 것이 이 도구의 핵심 요구사항 | 크롤링 실행 페이지 |
| **F002** | 크롤링 진행 상태 표시 | 진행률, 현재 처리 중인 언론사·기사 수를 실시간으로 표시 | Playwright 크롤링은 시간이 걸려 진행 상황을 알아야 테스트 도구로 쓸 수 있음 | 크롤링 실행 페이지 |
| **F003** | 수집 기사 txt 저장 | 크롤링한 기사(제목/URL/언론사/본문)를 실행 단위로 txt 파일에 저장 | 테스트 페이지이므로 DB 대신 txt 저장이 명시적 요구사항 | 크롤링 실행 페이지, 수집 결과 페이지 |
| **F004** | 수집 결과 목록/조회 | 저장된 실행(run) 목록과 기사 txt 파일 목록·본문을 조회 | 수집한 데이터를 확인해야 다음 단계인 키워드 분석으로 이어짐 | 수집 결과 페이지 |
| **F005** | 형태소 분석 기반 단어 카운트 | Kiwi로 조사·어미·접미사를 제거하고 명사(NNG/NNP)·영문(SL) 토큰만 추출해 빈도 집계. **1글자 토큰은 제외**한다 | 조사 제거 없이는 "삼성이"/"삼성을"이 다른 단어로 집계되어 핫 키워드가 부정확해짐. 1글자를 남기면 `것`·`수`·`점` 같은 의존명사성 잡음이 상위를 잠식한다(`docs/kiwi-verification.md` §6 실측) | 핫 키워드 분석 페이지 |
| **F006** | 핫 키워드 랭킹 | 집계된 키워드를 빈도순으로 정렬해 상위 랭킹 표로 표시 | 핫 키워드 조사가 이 프로젝트의 목적 그 자체 | 핫 키워드 분석 페이지 |

### 3. MVP 이후 기능 (제외)

- 크롤링 결과 데이터베이스 저장 (지금은 txt/JSON 파일 저장. 데이터가 쌓이기 시작하면 저장소 인터페이스만 교체해 DB로 전환 예정 — 데이터 모델 참고)
- 여러 실행 결과 비교, 키워드 시계열 트렌드 분석
- 키워드 CSV/엑셀 내보내기
- 언론사별 키워드 비교, 카테고리 자동 분류
- 예약 크롤링(스케줄링), 알림
- 회원가입/로그인/로그아웃 등 계정 기능 — 로컬에서 혼자 쓰는 테스트 도구이므로 불필요 (인증 관련 페이지·메뉴·기능 ID 없음)

## 🗄️ 데이터 모델

> 지금은 DB 없이 `fs` 기반 txt/JSON 파일로 저장한다. 각 모델은 "현재 저장 위치"와 "향후 DB 테이블"이 1:1로 대응하도록 필드를 설계해, 데이터가 쌓이기 시작하면 저장소 구현체만 교체하고 필드 구조는 그대로 옮길 수 있게 한다.

### Press (언론사)

언론사마다 수집 방식이 다르다. RSS를 제공하는 매체는 피드에서 기사 목록을 정확히 얻고, RSS가 없거나 폐지된 매체(네이버 뉴스 등)는 목록 페이지를 파싱한다. 그래서 `sourceType`을 판별자로 둔 **분기 타입(zod `discriminatedUnion`)**으로 설계한다.

**공통 필드**

| 필드 | 설명 | 현재 저장 위치 | 향후 DB 테이블 |
|------|------|----------------|----------------|
| id | 언론사 식별자(슬러그) | `data/press-sources.json` 배열 요소의 id | press_sources.id |

**RSS 경로에 대한 두 가지 전제**

- **RSS 피드는 Playwright를 쓰지 않는다.** XML은 JS 렌더링이 없으므로 `fetch`로 충분하다. 브라우저를 띄우는 비용은 `contentSelector`가 지정된 언론사의 원문 페이지 수집에만 든다.
- **인코딩을 직접 처리해야 한다.** 국내 언론사 피드 중 일부는 아직 EUC-KR로 내려온다. `fetch`의 기본 UTF-8 디코딩에 맡기면 한글이 깨지므로, `Content-Type` 헤더와 XML 선언(`<?xml ... encoding="..."?>`)에서 charset을 읽어 `TextDecoder`로 디코딩한다. `rss-parser`가 아니라 `fast-xml-parser` + 자체 정규화 계층을 고른 것도 이 디코딩 단계를 우리가 통제해야 하기 때문이다.
