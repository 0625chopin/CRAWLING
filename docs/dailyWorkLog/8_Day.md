### 리뷰가 실제로 값을 더한 지점

1. **화면 리뷰어가 중단 훅이 두 경로에 다 걸렸는지 직접 확인했다.** HTML 경로(`crawlHtmlPress`)는
   `hooks`를 가공 없이 넘기지만 RSS 전문 경로(`crawlRssPress`)는 `offsetHooks`로 다시 조립한다 —
   **한쪽만 걸려도 테스트가 통과할 수 있는 구조**였고, 리뷰어가 `press-crawler.test.ts:213`의 회귀가
   정확히 RSS 전문 조합을 태운다는 것까지 확인했다.
2. **화면 리뷰어가 `recovered` 회귀의 양방향을 확인했다.** 복구 경로에서 `true`인 것만 단언하고 정상
   경로에서 `undefined`인 것을 안 보면 **"항상 `true`"인 버그가 그대로 통과한다.** 세 어서션이 각각
   다른 값을 단언하는 것을 확인했다.
3. **저장소 계층 리뷰어가 `RunNotFoundError`의 호출 체인 전체를 추적했다.** `getRunProgress` →
   `recoverRunProgress` → `getRun` → `readRunMeta` 어디에도 예외를 다시 감싸는 `catch`가 없음을 확인 —
   **중간에 한 번만 감싸도 `instanceof`가 조용히 실패해 404가 500이 된다.**
4. **크롤 파이프라인 리뷰어가 시각 필드 경계를 검산했다.** "실행 시각도 서버가 포맷해야 하지 않나"를
   의심했다가, 데스크톱 와이어프레임(`14:32:05 → 14:38:41`)과 모바일(`14:32 → 14:38`)의 **포맷이 서로
   다르다**는 것을 찾아내 초안의 경계가 옳다고 판정했다.

## 발견·해결한 이슈

1. [화면 → 팀장 판단] **run 생명주기 예외를 문자열 메시지로만 구분할 수 있었다**(I-016). GET 라우트가
   `error.message.startsWith('실행을 찾을 수 없습니다')`로 404를 판정했다. 리뷰 결과 **지금은 문구가
   정확히 맞물린다** — 문제는 문구를 누가 다듬는 순간 **404가 조용히 500이 되고 lint·typecheck·build·test가
   전부 통과한다**는 것이다. 게다가 9일차 015A가 `abortRun`의 두 예외를 **또 문자열로** 갈라야 하는
   상황이었다. → 팀장 판단으로 그 위에 쌓기 전에 닫았다: `RunNotFoundError`·`RunNotAbortableError` 도입,
   `@/lib/crawler` 배럴에서 3종 재수출, 라우트를 `instanceof` 판정으로 교체(D-022). **한국어 메시지 문구는
   한 글자도 바꾸지 않았다** (재검증 저장소 계층·화면 양쪽 pass)
2. [화면 → 팀장 판단] **복구된 run이 개별 언론사를 "정상 완료"로 보이게 했다.** `recoverRunProgress`가
   `target`을 실제 목표치가 아니라 `collected`로 채워, 원래 20건 목표였다가 5건에서 끊긴 언론사가
   **"5/5건 · 완료"** 로 그려질 참이었다. 실행 전체는 `aborted`로 정확하지만 언론사별 줄은 거짓을 말한다 —
   **모르는 값을 확정치처럼 보여주는 것**이라 받아들이지 않았다. → `RunProgress.recovered?: boolean`
   추가(D-023). `target`을 `null`로 바꾸는 안은 기각했다 — 소비처 전부가 분기를 떠안는다 (재검증 화면 pass)
3. [크롤 파이프라인 자체 발견] **RSS 전문 경로의 `offsetHooks`가 `isAborted`를 빠뜨렸다** →
   `isAborted: hooks.isAborted` 추가, 그 경로 전용 회귀 1건 (재검증 화면 pass)
4. [저장소 계층 → 신규 이슈 등재] **I-014**(`CrawlRun`이 대상 언론사 이름을 스냅샷하지 않아 삭제된
