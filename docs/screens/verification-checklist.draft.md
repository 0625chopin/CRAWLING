   에만 찍히고 2회차에는 안 찍히는 것도 보조 증거로 같이 확인할 수 있다(로컬 dev 콘솔 접근 가능하면).

## R-4 · 키보드 전용 조작으로 1~5단계 재수행

1. 마우스 클릭 대신 `browser_press_key`(Tab / Shift+Tab / Enter / Space / 화살표)만으로 §1부 1~5단계의
   핵심 동선을 재현한다 — 언론사 추가 다이얼로그 진입·필드 이동·저장, 홈의 언론사 체크박스 토글·크롤링
   시작 버튼, 결과 화면의 파일 목록 이동, 키워드 분석의 "분석 시작"·불용어 삭제(🚫) 버튼.
2. 각 스텝 후 `browser_snapshot`으로 현재 포커스 요소의 accessible name을 확인해 의도한 요소에 포커스가
   가 있는지 판정한다(스냅샷의 포커스 표시 또는 `browser_evaluate`의 `document.activeElement` 조회).
3. 포커스 링이 시각적으로 보이는지는 `browser_take_screenshot`으로 확인한다(디자인 토큰 기반 아웃라인이
   실제로 그려지는지).
4. 다이얼로그(언론사 추가/삭제 확인)에서 포커스가 다이얼로그 밖으로 새지 않는지(포커스 트랩), Esc로
   닫히는지 확인한다.
5. `combobox`(실행 선택·run 셀렉터)가 화살표 키 + Enter로 선택 가능한지 확인한다.
6. 막히는 지점이 나오면 "R-4 실패"로 적지 말고 **해당 컴포넌트·Task 번호를 특정**해 이슈로 등록한다(이번
   회차에는 실행하지 않으므로 이슈도 025 본번에서 발견 시 등록).

## R-5 · 다크모드 토글 후 5개 화면 재확인

1. 헤더의 테마 토글(`components/layout/theme-toggle.tsx`)을 눌러 다크 모드로 전환한다.
2. `/`·`/press`·`/stopwords`·`/results`·`/keywords` 5개를 순회하며 `browser_take_screenshot`으로
   하드코딩 색상이 남아 라이트 전용으로 보이는 요소가 없는지 육안 확인한다(`docs/CONVENTIONS.md` §8의
   "하드코딩 색상 금지" 위반 여부).
3. `browser_evaluate`로 다크 모드 표시 속성(예: `document.documentElement.classList`에 `dark`류 클래스가
   붙는지, 혹은 `next-themes`가 쓰는 속성)이 실제로 바뀌었는지, 샘플 요소 몇 개의 `getComputedStyle`
   배경색이 라이트 모드 때와 다른지 확인한다.
4. `browser_console_messages`로 콘솔 에러·경고 0건을 확인한다.
5. 확인 후 **토글을 라이트로 되돌려 원상복구**한다 — 다음 워크스트림이 같은 브라우저를 이어 쓸 수 있으므로
   (I-029 참고, 다만 025는 단독 세션이 원칙이라 이 시점엔 이미 다른 워크스트림이 없어야 한다).
